# 电视播放器适配：把已发布弹幕变成同名 XML

本文件说明 Danmaku Simulator 的分发目录如何接入既有 Android TV 播放器。当前优先适配 **MzDKPlayer 的同目录、同基名 XML 机制**：播放器继续读取自己的视频，生成器只提供弹幕侧车文件。

**验证状态：**既有 home-media 项目的历史记录已验证，当贝 H5 Pro 使用一份私用 NAS 兼容构建，通过 HTTPS WebDAV 播放原片、原生 XML 弹幕及独立普通字幕。本项目新生成的弹幕、公开目录与下述 sidecar CLI **尚未在电视实机验收**。本轮只读核查文档与源码，没有连接、唤醒或操作盒子，也没有上传 NAS。

## 1. 已有能力与证据边界

| 路径或能力 | 已有证据 | 本项目应如何使用 |
| --- | --- | --- |
| 私用兼容版 + HTTPS WebDAV + 同名 XML | 2026-11-04 的既有真机记录通过；一个明确片源加载了 7,364 条真实弹幕，并与独立普通字幕共存 | 作为首选接入路线，复用现有播放器连接；新生成侧车仍需单独验收 |
| 原生弹幕暂停、前后跳转、退出续播 | 同一历史样本已做实际操作和日志核查 | 不重新实现电视播放时钟；未来检查新侧车在这些操作后的表现 |
| MzDKPlayer 本地文件与 HTTP(S) XML | 固定版本源码中存在读取路径；上游 README 说明同名侧车机制 | 可以形成适配目标，但不能将“代码存在”写成当前设备已经通过 |
| SMB | 上游有实现；该家庭环境此前的相关直连尝试未通过 | 不把原先的 SMB 目标写成已实现路线，也不要求为此修改现有共享 |
| VLC / Kodi 的 ASS | 既有本地短样本通过滚动 ASS 与中文字幕共存；NAS SMB 未由此证明可用 | 作为备选导出方式；它与原生 XML 是不同的显示路径 |
| 远端 catalog、任意独立 XML URL、生成弹幕上电视 | 尚未完成该新链路的实机验证 | 先在本地选择轨道、生成同名侧车，之后另做明确的部署和验收 |

历史验收只覆盖一个具体版本的片源及相应设备配置，不代表全库、其他剪辑、4K/HDR、实体音箱听感或长期播放均已验证。私用兼容构建的 NAS 认证与证书处理不属于本仓库的通用播放器代码，也不随本项目分发。

## 2. 播放器实际如何发现弹幕

核查基线是 MzDKPlayer 1.19.0 对应源码，以及既有 NAS 兼容补丁。上游源码归档 commit 为：

`efa3446d2310206e89a793b4d3b99faedd522ac9`

### 命名规则

电视播放页从**视频 URI**推导弹幕 URI：替换路径最后一段文件名的最后一个扩展名，其他 URI 部分保持不变。它不会读取本项目的 catalog 来寻找另一条弹幕 URL。

| 视频文件名 | 自动发现的 XML |
| --- | --- |
| `Episode.01.mkv` | `Episode.01.xml` |
| `movie.mp4` | `movie.xml` |
| `movie` | `movie.xml` |
| `.hidden` | `.hidden.xml` |
| `movie.` | `movie.xml` |

目录名中的点不参与替换。字幕仍可独立使用同名 `.ass` 或其他支持格式；不要把弹幕 XML 转成同名普通字幕后，误认为仍保留了独立弹幕层。

### 读取路径

| 视频来源 | XML 的读取方式 | 注意事项 |
| --- | --- | --- |
| 本地 `file://` | 由视频路径推导 XML，再用 Android 文件输入流读取 | 所核查 XML 分支没有 `content://` 处理；不要假设任意外部文件选择器 URI 都能自动发现侧车 |
| `smb://` | 同名 URI 交给 SMB 文件流 | 有源码支持不代表当前 NAS 的 SMB 兼容问题已解决 |
| HTTP(S)，来源类型为 `WEBDAV` | 同名 URI 交给已有 WebDAV 客户端，复用播放器的连接认证 | 私有认证保留在设备或私有部署配置，不放进公开 catalog |
| HTTP(S)，来源类型为 `HTTP` | 同名 URL 交给普通 OkHttp GET | 该辅助函数没有接收任意自定义 Header 的参数 |
| 其他 HTTP(S) 来源 | 同名 URL 使用 URL 输入流 | 不能据此承诺所有授权、重定向或证书场景均可用 |

`openHTTPLinkXmlInputStream(xmlUrl, sampleMimeType)` 是一个内部读取函数。它的存在**不意味着电视 UI 暴露了任意独立 XML 源入口**。已核查的内部播放路由只有视频来源、来源类型、文件名、连接名；外部 `ACTION_VIEW` 处理的是带 `video/*` MIME 的视频 URI，没有独立 `danmaku_url` 参数。

由此有两个直接限制：

- `https://media.example/episode.mkv` 会去寻找同源的 `episode.xml`，不会自动去另一台服务下载 `tracks/.../comments.xml`。
- 更改媒体 URL 的路径后，原查询串仍可能保留。绑定了具体对象路径的签名 URL 不应假设换成 `.xml` 后仍有效。公开视频绑定使用稳定网页地址；认证与临时签名属于私有交付环节。

播放器的 HTTP 文件浏览使用其自身支持的目录列表方式。一个 COS 对象目录或本项目的 `catalog.json`，不会自动变成它能浏览的 NGINX 文件列表。浏览器 CORS 设置也不会为电视播放器增加自定义源功能。

## 3. 分发目录与电视侧车之间的桥接

分发层保留多个媒体身份、轨道和不可变内容版本：

```text
catalog.json
tracks/<media_key>/<track_id>/<revision>/comments.json
tracks/<media_key>/<track_id>/<revision>/comments.xml
tracks/<media_key>/<track_id>/<revision>/comments.ass
```

电视适配只把**用户选定的一个轨道版本**投影为精确视频文件名对应的 XML。公开目录不用伪装成视频目录，也不需要把视频复制到弹幕服务。

一份视频的自动发现位置只有一个同名 XML。多种风格、不同模型或不同时间校准应继续保存在分发目录的不同轨道中；切换电视使用的轨道时，再替换选定的侧车。不要默默混入或覆盖已存在的原生弹幕。

### CLI 示例

先发布一个已生成的 run：

```bash
python3 -m danmaku_sim publish runs/episode \
  --library published --track-id tv --label "电视弹幕"
```

从输出或 catalog 中选出 JSON 轨道。下列路径中的占位段需替换为实际值：

```bash
TRACK_JSON="published/tracks/<media_key>/tv/<revision>/comments.json"

# 视频目录在本机可写时，准备同目录同名 XML。
python3 -m danmaku_sim sidecar \
  --track "$TRACK_JSON" --video "media/Episode.01.mkv"

# 只准备待部署文件，不接触 NAS。
python3 -m danmaku_sim sidecar \
  --track "$TRACK_JSON" --video "Episode.01.mkv" \
  --out-dir "staging/episode"
```

第二条生成 `staging/episode/Episode.01.xml`。`--track` 接受已发布的 `danmaku-track/v1` JSON；远端目录中的文件应先下载到本地，不能把 HTTP URL 当作本地路径参数。

`--video` 只确定目标文件名与默认输出目录，**不要求视频已经存在，也不验证片源身份**。它适合提前准备待部署侧车，但成功导出不能替代影片版本和时轴确认。本地视频路径不会写入公开 track 或 catalog。

不同内容的现有 XML 默认保留并报错；只有明确选择替换时才使用 `--replace`。若已有真实弹幕，更适合先用 `--out-dir` 生成候选，完成比较后再决定使用哪一份。相同内容可重复准备。

### 部署到既有 WebDAV 路线

本仓库的 sidecar 命令不负责 NAS 登录或上传。后续部署应复用已有私有工作流：

1. 明确选择目标视频及其版本，核对内容身份和时间映射。
2. 在本地生成 XML，检查条数、时间范围、可解析性和散列。
3. 检查远端精确同名目标。不存在时可使用条件创建 `If-None-Match: *`；已有不同内容时先保留，由用户明确决定替换。对已有资源的更新还应使用已取得的版本标识避免覆盖并发变更。
4. 完整上传后重新读取文件，比对字节或 SHA-256。不要把登录页面、错误页或未完成的上传当作 XML 成功。
5. 从播放器已保存的 WebDAV 文件列表打开原视频，并检查 XML 加载及显示。

XML 是进入播放页时加载的文件，所核查实现没有监听 catalog 更新的热切换协议。更换同名 XML 后应重新打开视频，不假设正在播放的会话会自动刷新。观看时媒体仍由盒子直接读取原 NAS；电脑不需要持续充当媒体中转。

本轮没有执行上述 NAS 部署步骤。

## 4. 时间坐标只转换一次

发布轨道的 JSON 保留原始弹幕时间，`timeline` 描述目标播放时轴：

```text
目标播放秒数 = 原始弹幕秒数 × scale + offset
```

`scale` 必须为正数；正 `offset` 表示延后。例如原始 10 秒的弹幕，`scale=1`、`offset=2` 时应在目标视频 12 秒显示。

| 格式 | 时间语义 | 消费者的职责 |
| --- | --- | --- |
| 已发布 `comments.json` | 原始时间 + `timeline` | 按目标时轴转换一次 |
| 已发布 `comments.xml` / `comments.ass` | 已写入转换后的时间 | 直接播放，不再次套用同一个变换 |
| sidecar CLI 生成的同名 XML | 从已发布 JSON 转换一次 | 与发布 XML 使用相同对齐规则 |

小于零或超出目标时长的条目应丢弃并计入报告，不全部挤到零秒或片尾。播放器把 XML 中的秒数转换为毫秒；这里的 `p` 时间不是 Unix 时间戳。

所核查 XML 弹幕设置包含开关、显示区域、字号、透明度和类型过滤，没有独立的 `scale` / `offset` 输入。普通字幕的提前或延后设置属于字幕轨，不应当作 XML 弹幕对齐接口。因此需要在导出或 sidecar 阶段完成校准。

### 片源匹配限制

- 相同标题、集号或近似时长只适合检索候选，不能证明是同一剪辑。
- BVID、page、CID 或网页绑定说明选择了哪个网页对象；它们不能自动证明本地 BD/WEB 版本与该网页时间线一致。
- 一条 track 只有一份时间变换。不同目标视频若需要不同变换，应发布分别校准的轨道，不能把多个不兼容的目标绑定到同一时间线。
- 固定偏移适用于整体平移；比例适用于确认过的均匀时间伸缩。片头删改、广告插入、重排或分段剪辑不能只靠一个偏移强配，需要新轨道或以后明确支持的分段映射。
- 至少检查开头、中段、后段的对应画面或声音锚点。既有记录曾对一个片源做七处预览时间窗对照并保留零偏移，这只是该样本的结论，不是所有版本天然对齐的保证。

## 5. XML 兼容范围

本项目优先导出普通滚动模式 `1`，与现用渲染路径直接对应。XML 使用 UTF-8，文本由 XML 序列化器转义；保持原始 JSON 作为内容来源，不用字符串替换临时修改 XML 时间。

`<d p="...">文字</d>` 中的主要字段如下：

| 字段位置 | 含义 | 本项目约定 |
| --- | --- | --- |
| 1 | 出现时间，秒 | 已对齐的非负播放时间 |
| 2 | 模式 | 首版电视兼容优先使用 `1` |
| 3 | 字号 | 整数 |
| 4 | RGB 颜色 | 十进制整数，如白色 `16777215` |
| 5 | 发送时间戳 | 合成弹幕可用 `0`，不冒充真实发送时间 |
| 6 | 弹幕池 | 普通池 `0` |
| 7 | 用户标识哈希 | 虚拟观众标识，不是真实账号 |
| 8 | 行 ID | 稳定且互不相同的正整数，适配有符号 64 位读取 |

XML 元数据标识合成来源，不把生成评论包装成平台原始观众评论。

固定源码版本的渲染映射对模式 `4` / `5` 的上下位置与常见 B 站约定相反；当前普通滚动导出规避了这一区别。未来增加顶部、底部或其他模式时，应按实际播放器版本验收，不能只凭格式名称假定所有端的显示一致。BAS/高级弹幕不在首版兼容承诺中。

### ASS 备选路线

VLC / Kodi 的既有本地实验说明可以用 ASS 显示滚动文字，但并未证明该环境的 NAS SMB 路线可用。如果普通字幕和弹幕都由字幕轨承载，应明确合成为一份 ASS 的不同样式/事件，不能假设播放器可同时选择两个独立字幕轨。

对 MzDKPlayer 的首选路线，保留 XML 弹幕与普通字幕分层；无需转码或把弹幕烧进视频。

## 6. 下一次实机验收应证明什么

本节是未来验收清单，不是本轮已完成事项。

- 同一目标文件的内容身份、选中 track/revision、时间变换和最终 XML 散列能够对应。
- 播放器真实加载数量与导出数量一致，并实际显示新生成的内容。
- 暂停、前跳、后跳、退出续播后，弹幕跟随媒体位置；独立普通字幕仍可使用。
- 在开头、中段、后段检查语义与时间；区分原始生成问题、片源映射问题和显示拥挤问题。
- 默认保护既有侧车；更换后能够依据私有部署记录恢复原文件。

播放器支持更多网络协议、倍速或高级媒体特性，不等于本次组合已逐项验证。验收结果应写明具体设备、播放器版本、媒体版本与测试范围，公开报告只保留适合共享的结果。
