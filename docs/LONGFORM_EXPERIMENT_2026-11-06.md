> 实测日期：2026-11-06。生成时的代码基线：`740062e`。实测后的逐尝试响应归档修复为 `5dccc03`，已推送并通过 CI；它没有改变这次生成输入或已有费用。
>
> 当前状态：完整分析、独立生成、互动的代理辅助内容审查及 NAS 条件写和读回核验已经完成，最终轨道为 2,803 条。当贝盒子已实际载入全部弹幕，片头可见弹幕、暂停恢复和长距离跳转后的对应片段显示均通过验收。实机验证覆盖片头与约一小时处两个窗口，没有连续观看完整 91 分钟，也没有独立人类质量评测。

这次实验把一部 91 分 30.256 秒的中文长片处理为可以导出的模拟弹幕轨道。完整分析包含 1,246 条对白与 459 条画面观察，独立生成覆盖全片；对已出现弹幕另做少量接话，受控复读通过本地调度添加。最终版本为 2,509 条独立弹幕、200 条受控复读、94 条互动，共 2,803 条，平均 30.63 条/分钟。

## 2. 从字幕与画面取得可用证据

### 对齐质量比时间戳字段的粒度更重要

首先对中文音轨做了完整句级 STT：120 秒核心分块，边界各 1.5 秒重叠，共 46 次实际请求，45 次有转写、1 次无对白。账本发送音频总时长 5,625.256 秒，包含分块重叠。

这份中文转写适合交叉核对内容，但有些字幕段横跨约 40 秒。如果把它们的结束时点当作观众首次获得信息的时点，反应会明显迟到。因此又试了一次首块词级 STT。API 成功返回 149 个时间单元，但其中一个单字符单元覆盖 18.70–36.18 秒，长达 17.48 秒；与声画及字幕锚点对照，还发现了片头旁白错位。此次词级小试验仅调用一次，未继续处理全片。

最后采用已经核对的英文对白字幕作为生成时序证据，共 1,246 条。非对白注释、制作名单与歌词没有当成对白导入；中文粗转写只作私有交叉验证。没有额外调用模型逐句翻译字幕。

这说明 `timestamp_level=word` 只规定返回粒度，不能保证强制对齐准确。对已有可信字幕的长片，先检查时间锚点、复用字幕，可能比重复跑全片语音识别更合适；本例不能证明所有片源的字幕都可靠。

### 画面覆盖与并行处理

抽帧使用均匀采样，间隔 12 秒、最多 480 帧，实际得到 459 帧，覆盖 0.300–5,490.156 秒。单张图作为该时点的画面证据；它本身不能确认连续动作或未采集的声音。视觉描述保留不确定性，但这不能保证模型从不误推断。

视觉并发为 3。此次使用私有编排让 STT 与视觉并行：STT 使用自己的音频分块目录，视觉保留独立的阶段状态，两者通过同一客户端记账。最终组装标准分析时复用相同帧与成功响应缓存，459 次视觉本地命中，0 次新 API 请求。并行方式没有改成通用 CLI 的默认行为。

均匀抽帧保证覆盖全片，但 12 秒间隔仍可能错过短促动作、表情或画面文字。当前视觉结果不是逐帧理解，也不承担精确镜头切分。

## 3. 冻结的生成与调度配置

以下是本次实测配置，不是对所有视频的推荐默认值。

| 项目 | 配置 |
| --- | --- |
| 观众 | 4 类：普通观看、细节观察、轻松吐槽、情绪反应 |
| 观众权重 | 1.0 / 0.65 / 0.85 / 0.8 |
| 模型分配 | 前两类使用 MiniMax-M3.1-Flash，后两类使用 deepseek-flash |
| 检查点 | `checkpoint_mode=events`；`event_merge_seconds=4` |
| 历史证据 | 最近 45 秒；只包含当时已经可用的事件 |
| 独立采样 | 1 轮；每次请求最多 1 条，允许沉默 |
| 文本长度 | 独立弹幕最多 14 字符 |
| 并发 | 总并发 12；私有客户端对两个供应商分别限制为 6 |
| 反应与时限 | 初始反应延迟 0.35–1.6 秒；检查点后最晚 7 秒 |
| 密度 | 任意半开一秒最多 3 条；全片按 35 条/分钟计算总上限 |
| 受控复读 | 独立弹幕数量的 8%；仅父句不超过 8 字符；父后最多 2 秒 |
| 互动 | 独立弹幕数量的 4%，最多 128；实际预算 100 |
| 互动时序 | 至少 0.4 秒读父弹幕，再加反应时间；父后最多 3 秒 |
| 互动约束 | 一层回复；每父/每源事件至多一次；不同观众接话；间隔至少 40 秒 |
| 随机种子 | 20261106 |

独立观众的请求彼此不可见。互动是独立采样结束后另开的阶段，只看到一条已经出现的父弹幕和此刻之前的证据；不重新生成基础弹幕。复读是调度器产生的受控副本，不额外调用模型。因局部密度挤不进时，复读或互动可以被丢弃。

每次请求只传入当前检查点允许的证据，不传片名或全局剧情梗概。字幕以结束时点作为可用时间，画面观察以对应帧时点作为可用时间，输出还保留知识截止、源事件与父子关系。详情见 [架构说明](ARCHITECTURE.md)、[互动说明](INTERACTIONS.md) 和 [调度器](../danmaku_sim/scheduler.py)。

### 两次前缀试验怎样影响最终配置

早期前缀允许每次最多 2 条、最长 18 字符。该轮共 263 次真实请求，参考费用 $0.07529204。中途 249 份回执中，176 次返回两条、73 次返回一条，没有沉默；此外还出现了评论“翻译腔”和自行翻译未确认中文专名的问题。该版本没有进入最终轨道。

因此把上限改为每次 1 条、最长 14 字符；观众说明固定为中文原声观看，英文只作后台证据，不评论翻译，未经确认的中文专名使用指代。新的短前缀有 95 个逻辑请求，94 个成功、1 个返回空白响应；成功结果组成 94 条独立弹幕和 7 条受控复读。该轮参考费用 $0.02683842。

完整分析通过真实生成引擎加离线记录客户端预先计算，准确计划为 **2,561 次逻辑请求**：MiniMax 1,261、DeepSeek 1,300。95 个修订前缀请求与全片对应请求身份完全一致，其中 94 个成功缓存被正式全片运行复用。旧 263 次与接受配置的缓存键没有交集。

`comments_per_window` 是每次请求的输出上限，不是产量保证；改变它会改变缓存身份，也不直接减少逻辑请求数。`target_per_minute` 是本地调度容量，同样不能用它当作前置 API 预算。

首轮 8 个独立生成失败的供应商响应状态都是 `completed`，但正文是普通文本，未通过 JSON 解析。互动的 4 个失败尝试也都有供应商完成回执，却没有通过回复有效性校验。因此：

- 供应商账本的 `failed_requests` 不能代表所有逻辑任务失败。
- 接受配置的独立生成实际调用 2,570 次，包含 2,561 个最终成功任务与 9 个失败尝试：1 个空白响应、8 个解析失败。
- 互动实际调用 104 次，得到 100 条有效回复；4 次校验失败的用量仍保留。
- 恢复只重发失败项。成功结果从本地响应缓存复用，命中次数不计新请求、不重复计费。

### 响应归档的缺口与实测后修复

本次 8 个全片解析失败和 4 个互动校验失败的原始响应，都在重试前单独归档；首次失败结果及诊断也保留。但 95 请求修订前缀中的那次 DeepSeek 空白响应没有这样的独立原始存档。旧实现把同一请求键的回执写到同一路径，后续成功重试覆盖了兼容文件；现在只能从用量行和诊断确认那次失败，不能复原其完整响应正文。因此本次历史材料并非每个失败尝试都具有完整原始响应。

发现后在提交 `5dccc03` 中对 [ModelClient](../danmaku_sim/providers.py) 做了小范围修复：每次实际收到文本/视觉模型响应后，先用随机且排他创建的文件名保存原始字节；用量行记录相对路径、SHA-256、字节数和响应体截取标记。文件名不使用供应商 request ID，同一 ID 或同一缓存键重试也不会覆盖之前的逐次存档。原有 `responses/<cache_key>.json` 仍保留为最新可解析回执的兼容入口，不能把它当历史档案。

新增覆盖范围包括空文本、模型输出达到长度上限、无效 JSON、HTTP 错误正文、响应体读取中断和读取上限截取。本地缓存命中不伪造新尝试；磁盘归档失败会保留已收到的用量并明确报错，不把该响应写成可复用成功结果。针对同键失败后重试、重复且含路径字符的 request ID、正文保真与费用不变的离线回归已通过；完整 Python 回归为 92 项。修复没有重新调用模型，也没有改变本次已有用量或费用，已经被覆盖的历史正文无法由此补回。

## 7. 内容质量：检查到什么，还不能证明什么

本次内容审查由本对话的内置代理阅读文本、来源证据和定点截图完成，没有独立人类评审。这是工程 QA，不是人类观看评测，也没有测量真实用户的满意度。

独立弹幕的代理辅助审读覆盖 261 个去重后的候选，结合全片不同位置的分层抽样、专名和确定性风险筛选、视觉描述筛选以及恢复后新增候选。对部分判断又核对了 6 张原始帧。自动关键词只帮助定位，没有作为全局黑名单。

已确认的问题主要是未经可靠依据的中文专名、英文证据被直译、个别视觉判断过强，以及少量无趣的画面复述。最终按具体证据制定精确的事件与文本规则删除候选，保留原始数据与处理记录。因为抽样包含针对风险的主动筛选，24 条删除数量不能直接当作整片模型错误率。

新配置在已审范围内没有继续出现评论翻译质量的内容，也没有发现明确的未来剧情泄露。结构检查还逐条验证了时间、知识截止与源事件关系。但模型可能带有训练知识、作出错误猜测或把不确定观察说得过满，因此不能把结构通过宣称为全部语义无剧透。

文字风格仍有可见的模板倾向，例如“有点吓人”“压迫感拉满”“这话说得”等句式。原始 2,533 条独立候选中有 2,462 种不同文本，精确同文的重复余量为 71；同文重复和有意添加的 202 条原始复读是两种不同来源。当前没有做全片语义去重，避免抹掉少量正常共鸣；也不把这样的输出描述成已经达到真人弹幕水平。

全部 100 条互动均经代理辅助定点审读，删除 6 条，保留 94 条。删除项中，3 条属于具体语义或术语问题，包括未实际回答父问题、误解词义和猜错中文专名；另 3 条更接近说明文字或画面复述。删除依据是具体上下文，不是整类词汇的全局禁用。原始互动、父弹幕、源证据和精确删除理由均有私有记录。

## 8. NAS 与电视端播放器验收

导出、远端存储和设备播放是三个独立结果，分别取证。播放设备为当贝盒子，使用 MzDKPlayer NAS 兼容版。

### 已定位的 NAS 目录兼容问题

NAS 的 PROPFIND 响应实际包含目录自身、影片和同名 XML 三项，但影片及 XML 的 DAV href 含裸方括号 `[]`。播放器使用的 Sardine 0.9 中，`ResourcesResponseHandler` 静默忽略了这些无法按原样解析为 URI 的文件项，只留下目录自身；APP 去除自身目录项后，文件列表就成了空列表。这是目录解析问题，不能据此判断 NAS 没有影片或弹幕文件。

播放器现有 NAS 客户端已经做了有界兼容修复：仅处理 PROPFIND 的 207 响应中的 DAV href，规范化过程设 4 MiB 处理上限；保留已有 `%HH` 转义、合法 URI、IPv6 地址及原有认证/TLS 行为。13 / 13 个针对性用例通过，真实 NAS 响应重放也已确认原实现接受 1 / 3 项、修复后接受 3 / 3 项。新 APK 已 assemble 成功，签名和包名与已安装版本一致，随后通过原位安装完成更新。检查的连接偏好与应用设置文件在安装前后字节摘要一致。真机新进程已实际列出正确的 MKV 与 XML 两项，目录解析阻塞已经在设备上解除。打开目标影片后，当前进程日志记录载入 2,803 条弹幕并传给播放器；屏幕显示与暂停、恢复、跳转检查也已通过。

## 9. 这次实验支持的结论

本例已经证明：现有流程可以覆盖一部 91 分钟长片，在两个模型独立采样后添加受控复读和少量互动；可以在解析或校验失败后只重发失败项，复用已成功前缀，并把真实请求、供应商缓存、本地缓存和失败用量分别记清。以可信字幕为起点，本次实际生产路径的参考费用低于 $1。

成本之外，对齐证据和代理辅助内容审读是此次主要质量约束。细化 STT 时间戳没有自动解决对齐问题，已有字幕需要核对而不是直接信任；缩短输出与限定专名能改善首版结果，但仍有模板化表达和个别错误。12 秒视觉采样与一次 261 候选抽样不足以证明全片内容逐条正确。

这是一部素材、一次配置的实测记录，不是多视频质量基准。设备加载和同步结果单列在第 8 节，与生成、结构校验和远端读回分开记录。
